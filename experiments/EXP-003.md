# EXP-003 — Scan kernel throughput on a synthetic 10 GiB image

- **Date:** 2026-09-15
- **Milestone:** M2 DoD "≥200 MB/s single-core on a synthetic 10 GiB image"
  (plan.md §5), catalog.md M2a entry
- **Script:** [`experiments/bench_scan.py`](bench_scan.py); environment:
  [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-003/` (gitignored): `env.txt`,
  `image.json`, `results.json`, `stdout.txt` and `profile_full.txt`. The
  image itself was deleted after the runs (`clean`); `generate` rebuilds it
  byte for byte.
- EXP-002 is reserved for the discard trio (M2b).

## 1. Hypothesis

On one core, the numpy scan kernel scans a 10 GiB image whose tree-block
density resembles a filesystem's (about 2 % of the image) at ≥ 200 MB/s. This
holds for the prefilter alone and for full validation, with a cold and with a
warm page cache.

## 2. Method

- **Kernel under test.** `btrfska.scan.kernel_numpy` at commit `7571f89`,
  `workers=1` (one process), over one region covering the whole image, probing
  every 4 KiB offset.
  - **prefilter**: `iter_prefilter_hits`. Two strided u64 compares per window
    of 65 536 offsets through a view of the read-only map.
  - **full**: `iter_candidate_nodes`. The prefilter, then for every hit a
    16 KiB copy, `check_block` (csum and every header and layout check) and a
    chunk-map lookup. The chunk map is empty, so every lookup misses.
- **Cache states.**
  - **cold**: `posix_fadvise(POSIX_FADV_DONTNEED)` on the image before the
    run. It needs no root, because the benchmark owns the file.
  - **warm**: the run follows one that has just read every page.
  - The fraction of the image's pages in the page cache is measured with
    `mincore()` right before each timed run, not assumed.
- **Schedule.** N = 5 rounds. Each round runs cold prefilter, warm
  prefilter, cold full, warm full, in that order. Every run opens a fresh
  image handle (a fresh map), so each run pays its own page faults. The
  process was not pinned (affinity: all 12 logical CPUs).
- **Metrics.**
  - Throughput is image bytes divided by wall-clock seconds, in MB/s
    (10^6 B/s, the DoD's unit) and MiB/s.
  - CPU seconds are `time.process_time()`.
  - Each run also records its hit and valid counts, which must equal the
    generator's (11 151 hits; 11 151 − 106 corrupted = 11 045 valid).
- **Success.** Every cell's median is ≥ 200 MB/s and every run's counts
  equal the generator's.
- **Bottleneck.** `profile --mode full` runs one warm full scan under
  cProfile.

## 3. Image

The image is synthetic, not from `corpus/vm`, so it has no `corpus/manifest.tsv`
row. `bench_scan.py generate` builds it deterministically from these parameters
(`image.json`):

| Parameter | Value |
|---|---|
| size | 10 737 418 240 B (10 GiB), 160 tiles of 64 MiB |
| seed | 3 (Python `random.Random`) |
| metadata tiles | 6: 16 KiB slots, each filled with probability U(0.2, 0.9) drawn per tile |
| data tiles | 80: random bytes |
| hole tiles | 74: never written (sparse) |
| node pool | the 84 valid scan candidates of `sandbox.img` (crc32c, nodesize 16 KiB); pool SHA-256 `40cf88e93eacfe100bfe55878738dec96ab9d20eabd45bac2e1474670a702602` |
| corrupted copies | 1 % target: one byte flipped after the header fsid, so a copy stays a candidate and fails its csum |
| tree blocks written | 11 151 (106 corrupted) = 174 MiB, 1.6 % of the image |
| allocated on disk | 5 771 366 400 B |
| image SHA-256 | `acf9b2ef712d3c78564888e0e1b0efc04db4129982b5d64c261e4c9424bc25e1` |

- Copied blocks keep valid checksums: a tree block's checksum does not
  cover its physical location.
- Generation took 28.0 s. `generate --verify` recomputed the same SHA-256
  without writing (26.2 s wall).
- `sandbox.img` was only read, and its hash is unchanged (catalog.md
  verification table).

## 6. Results

N = 5 per cell. Entries are median (min–max). The whole `run` took 52.8 s
wall, of which 5.8 s user and 27.5 s system CPU (shell `time`, including the
untimed node-pool scan).

|---|---|---|---|---|---|---|---|---|---|

| prefilter | warm | 5 | 6138.6 (3622.4–8364.7) | 5854.2 (3454.5–7977.2) | 1.75 (1.28–2.96) | 0.88 (0.55–1.78) | 0.8978 (0.8171–0.9259) | 11151 | — |
| full | cold | 5 | 3277.1 (3227.5–3337.8) | 3125.2 (3078.0–3183.2) | 3.28 (3.22–3.33) | 2.11 (2.01–2.14) | 0.0000 (0.0000–0.0000) | 11151 | 11045 |
| full | warm | 5 | 5691.0 (4430.1–7025.2) | 5427.3 (4224.9–6699.8) | 1.89 (1.53–2.42) | 1.07 (0.89–1.18) | 0.9092 (0.8735–0.9280) | 11151 | 11045 |

- **DoD met.** The slowest single run (full, cold) reached 3 227.5 MB/s,
  16× the 200 MB/s target. Every run found exactly the generator's 11 151
  blocks and 11 045 valid ones.
- **Warm runs were not fully cached.** Between 7 % and 18 % of the pages had
  been reclaimed before each warm run: the 10 GiB cache competes for 15.3 GiB
  of RAM. The profiled run started with 99.88 % of pages cached and took
  0.883 s wall, 0.849 s CPU (12 156.7 MB/s). The warm medians therefore
  understate a fully cached scan, and their wide range tracks the cached
  fraction.
- **Bottleneck.**
  - **Cold.** Reading the 5.8 GiB of allocated blocks from NVMe: wall exceeds
    CPU by 1.1–1.2 s in both cold cells.
  - **Overall.** Page-fault and page-cache work in the kernel. System CPU
    (27.5 s) was almost five times user CPU (5.8 s) over the whole run,
    including the cache drops and refaults that the cold runs force.
  - **In the process** (profile, fully cached, 0.95 s under cProfile):
    - per-candidate work in `_record` takes 0.680 s cumulative, of which
      `check_block` is 0.536 s and its per-item layout checks 0.197 s. That
      is about 61 µs per candidate, in Python;
    - the numpy prefilter (`_window_hits`, 40 windows) takes 0.185 s;
    - crc32c itself takes 0.014 s.
  - **Scaling.** Validation cost grows with the number of candidates, the
    prefilter's with image size. No optimisation was needed for the DoD.

## 7. Threats to validity

- **Internal.**
  - Timing jitter on a hybrid CPU (P and E cores, process not pinned) and
    partial page-cache reclaim in warm runs; the cached fraction is reported
    per run.
  - The cold state was produced by `POSIX_FADV_DONTNEED`, not a reboot.
    `mincore()` confirmed 0 cached pages, but device-level caches were not
    controlled.
  - `hits` and `valid` equal the generator's counts in all 20 runs, so the
    speed was not bought by skipping work.
- **External.**
  - The image is sparse: 4.97 GiB of holes read as zeros without device
    I/O, so a dense image of the same size needs more read time when cold.
  - The storage is one consumer NVMe drive on ext4. HDDs or network storage
    will be I/O-bound far sooner (plan.md §9).
  - Tree blocks come from one image (crc32c, 16 KiB); other checksum types
    cost more per candidate (sha256, blake2b).
- **Construct.**
  - Tree-block density was 1.6 % of the image. Per-candidate validation is
    the largest in-process cost, so a metadata-dense image is slower.
  - Extrapolation, not measured: at 61 µs per candidate, a 10 GiB image made
    entirely of 16 KiB tree blocks (655 360 candidates) would need about 40 s
    of validation, about 270 MB/s. A density sweep is a follow-up.
  - The empty chunk map makes each lookup a bisect miss. Real maps with many
    chunks cost more per candidate.

## 8. Status

**Supports** the hypothesis. The M2 performance DoD is met with a large margin
in all four cells. Follow-ups:
- a tree-block density sweep (dense images) to measure the validation
  bound;
- a pinned-core run on a P core;
- a non-sparse image on the same drive;
- multi-worker scaling, which is not measured by default because of the
  host's CPU-load limit.
