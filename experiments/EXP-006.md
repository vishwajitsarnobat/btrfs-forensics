# EXP-006 — Which recovery source gives back which file, on a history deeper than the backup roots

- **Date:** 2026-09-21 (registration and results)
- **Milestone:** M4, definition of done ("deleted files recoverable from (a) anchored historical
  roots, (b) orphan nodes and (c) orphan items, each labeled with its source; on the
  beyond-4-generations image (b)/(c) recover a file that (a) cannot"); claim C1 as narrowed by
  EXP-005
- **Script:** [`experiments/exp006.py`](exp006.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-006/results.jsonl` (gitignored), one line per build
- **Registration:** §1 and §2 were committed before the script was run. **This is not a blind
  registration.** The scenario was developed on trial builds (eight, on the dev host), and what
  they showed shaped it twice: the first version's "files only orphan leaves can give" turned out
  to be an artefact of a 64-state bound in our own discovery (catalog.md, M4d), and flash files
  were added after that, when a natural history gave no such file. The predictions below are
  therefore informed by those trials; what the five runs add is the median and the range.

## 1. Hypothesis

On a filesystem whose history runs deeper than the four backup roots and was never balanced:

- **H1 (anchored roots beyond the backups).** Most deleted files that were ever committed are
  recoverable from a root tree the scan discovers, and almost none from the current and the four
  backup roots. Registered: of 24 victims, each committed in exactly one generation, at most 4
  come back from the current or a backup root, and at least half come back only from states
  beyond them.
- **H2 (orphan file-tree leaves add no committed file).** No victim is recoverable *only* from an
  orphan leaf. A victim's leaf and the root tree of its generation are allocated side by side, so
  they survive or die together. Registered: 0 victims only from an orphan leaf.
- **H3 (dropped log trees).** A file written, fsynced and deleted within one transaction was
  never in a committed tree, so no root gives it back; the leaves of the log tree that the next
  commit dropped do, as long as they are not overwritten. Registered: 0 of 8 flash files from
  any root; at least 6 of 8 only from an orphan leaf, the last ones written being the surest.
- **H4 (ORPHAN_ITEM).** The file unlinked while open at the last commit comes back, hash-exact,
  labelled `orphan_item`. Registered: in every build.

**What would refute it.** A flash file among the artifacts of an anchored root (then it was
committed after all, and the scenario does not do what it says); a victim only an orphan leaf
gives (then H2's explanation is wrong, and C1 gets a stronger claim); fewer than half of the
victims from states beyond the backups (then deep histories are less recoverable than the
trials suggested).

**What it means for the paper.** H1 is the file-level form of N5/N10: discovered states matter,
backup roots do not. H2 and H3 together say what "recovery from orphan nodes" is worth on a
modern kernel: not committed files whose root trees died, but what was never committed at all:
mid-transaction versions (catalog.md, M4d) and fsynced-then-deleted files. That is a narrower
and more defensible C1 than the prototype's.

## 2. Method

**Scenario.** `corpus/vm/scenarios/deep.guest.sh`, the recipe of corpus image `m4_deep`: pinned
`mkfs.btrfs` 6.6.3 (`--csum xxhash`), guest kernel 7.0.0-31, 512 MiB, `commit=300`, no
compression, no balance, no discard. 48 subvolumes; 400 inline padding files; 24 rounds of
(create a victim, commit, log its SHA-256, delete it, commit, rewrite a seventh of the padding
files, commit); every sixth round two flash files (fsync, log the hash, delete, no commit in
between); finally a file unlinked while open, a commit, and power-off without unmount.

**Builds.** Five fresh builds (a guest run is not bit-stable, CONTRIBUTING.md §5), each measured
and deleted. The corpus image `m4_deep` itself is measured too, as a sixth line, for the record.

**Measurement per build.** `catalog build --full-sweep` (every root tree evaluated; a build where
the state bound was hit is reported as such), then `recover --root all --orphans --tree all`. A
logged file counts for a source when an artifact of that source has status `complete` and the
logged SHA-256. Sources: `backup` (a state the superblock or a backup slot names), `beyond` (any
other cataloged state), `orphan` (`orphan_node`), `item` (`orphan_item`). The image's hash is
taken before and after.

**Reported.** For every quantity the median and the range over the five builds, and the host.

N = 5 builds on one host; no build hit the state bound; every image unchanged.

|---|---|---|
| superblock generation | 93 | 93–93 |
| states (root trees evaluated) | 79 | 78–80 |
| of them named by the superblock or a backup slot | 4 | 4–4 |
| orphan leaves | 344 | 343–345 |
| victims | 24 | 24–24 |
| victims from the current or a backup root | 0 | 0–0 |
| victims only from states beyond them | 21 | 21–21 |
| victims only from an orphan leaf | 0 | 0–0 |
| victims not recovered | 3 | 3–3 |
| flash files | 8 | 8–8 |
| flash files from any root | 0 | 0–0 |
| flash files only from an orphan leaf | 8 | 8–8 |
| flash files not recovered | 0 | 0–0 |
| open-unlinked file as `orphan_item` | 1 | 1–1 |

The corpus image `m4_deep` of this build gives the same line: 78 states, 345 orphan leaves,
0 / 21 / 0 / 3 victims, 0 / 8 / 0 flash files, 1 orphan item. Its three unrecovered victims are
`victim_1`, `victim_2` and `victim_3`, the oldest: root-tree blocks of generations 4 to 16 are
gone from the image, and so are those victims' leaves.

- **H1 holds.** No victim comes back from the current or a backup root (the last victim was
  deleted six commits before the end). 21 of 24 come back, complete and hash-exact, from states
  that only the scan discovers, inline and regular ones alike.
- **H2 holds.** No victim is recoverable only from an orphan leaf, and the three that are lost to
  the roots are lost to the orphan leaves as well, as the side-by-side allocation predicts.
- **H3 holds.** No flash file appears under any root, complete or not, in any build. All 8 come
  back complete and hash-exact from leaves of dropped log trees, in every build, including the
  two from round 6, which about 70 later commits did not overwrite.
- **H4 holds** in every build.

## 7. Threats to validity

- **Internal.** One scenario on one host class; the spread across builds is tiny because the
  scenario is short and deterministic apart from the allocator. The GitHub runner has given
  other counts on other scenarios (CONTRIBUTING.md §5); the corpus tests therefore assert the
  claims and not these numbers. The separator files that protect the regular victims' data are a
  construction: without them a later victim reuses the hole, and the regular victims come back
  `partial` (seen in the first trial). The 3-of-24 loss is a property of this layout, not a rate.
- **External.** A 512 MiB filesystem a few seconds old, no balance, no discard, no concurrent
  writers, inline padding files so that data space is never under pressure. On an aged or busy
  filesystem metadata is reused faster and log-tree leaves are overwritten sooner; how much
  sooner is M7's question. With `discard=sync` EXP-000 and EXP-002 found almost no stale metadata
  at all, and that applies to dropped log trees too.
- **Construct.** "Recovered" means complete and hash-exact against the scenario's own log. A
  source is credited only when an artifact of that source is complete; a partial file counts as
  not recovered. "Only from an orphan leaf" is relative to *every* root tree the scan found
  (no build hit the state bound), not to the four backup roots, which would flatter the result.

## 8. Status

**Supports H1 to H4** (not blind, see Registration). What the paper may say from it, on this
corpus: on a deep, unbalanced history the backup roots recover none of the deleted files and
discovered states recover most (21 of 24); orphan file-tree leaves add no committed file; files
that were fsynced and deleted within one transaction are recoverable only from dropped log-tree
leaves (8 of 8), which nothing that walks down from a root tree can reach, because no root tree
ever named them; and an open-unlinked file is recoverable and identifiable through the
kernel's ORPHAN_ITEM.

Not tried, so not claimed (**UNVERIFIED**): whether `btrfs-find-root -o` with the log tree's
objectid, followed by `btrfs restore`, can be made to read a dropped log tree. It belongs in the
baseline comparison of M7.

Follow-ups: the same on aged, balanced and discard-enabled filesystems (M7); how long dropped log
leaves survive under metadata churn; which subvolume a log leaf belongs to (M5).
