# EXP-013 — Data-checksum verdicts of recovered files, per source, on the corpus

- **Date:** 2026-10-07 (registration, then results the same day)
- **Milestone:** M6a (plan.md "M6a: verify recovered content against EXTENT_CSUM"); claim C4
  (csum-tree-verified content), input of the M6c confidence tiers
- **Script:** [`experiments/exp013.py`](exp013.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-013/results.jsonl` (gitignored), one line per image
- **Registration:** §1 and §2 were committed before the script was written or run. **Not blind:**
  while the verification was built, `recover --root all --tree all --orphans --logs` was run on
  `sandbox.img` and `m4_deep` by hand. That run found a fault: ten anchored victims of
  `m4_deep`, hash-exact against the guest's log, were called `mismatch`. In each the sector that
  holds the end of the file had been written again past the end by a later, longer victim at the
  same address (the victims share their first bytes). The kernel zeroes the rest of that sector
  before it checksums it (extent_io.c:1857-1858), so the tool now also tries the sector with the
  bytes past the end zeroed and reports `tail_rewritten` when only that matches. After the fix
  the hand run gave on `m4_deep`: anchored `match` 27, `no_csum` 1 599; `log_tree` `match` 4,
  `no_csum` 4; `orphan_node` `match` 4, `no_csum` 408; no `mismatch`. Those numbers were seen
  before this registration.

## 1. Hypothesis

A recovered file's data checksum, looked up in the csum tree of the state it was recovered
from, separates the files whose bytes are the ones the filesystem wrote from those whose bytes
changed since, without false alarms on intact content.

- **H1 (the current state matches).** On every corpus image, every file of the current state
  (an `anchored_root` artifact of the state the superblock names) that has data on disk and
  checksums is `match`; none is `mismatch`, `partial_match` or `unavailable`. The one registered
  exception: `damaged.txt` of `m6_datacsum_flipped`, flipped on both mirrors, is `mismatch`.
- **H2 (no false alarm).** No artifact whose SHA-256 is a hash the scenario logged for a file is
  `mismatch`, on any image, any source. (The logged hashes are of the files as written; a
  recovered file with that hash holds the bytes that were checksummed.)
- **H3 (no false confirmation).** No `match` artifact of a file name the scenario logged has
  another hash than the one logged for that name, where the name was written once (registered:
  0; files written more than once under one name, the victims of `m4_deep`, are excluded).
- **H4 (stale states).** Files of older states that a later trim or overwrite reached are
  `mismatch` or lose their checksums: `s01_discard_sync_r1` has at least one `mismatch` or
  `unavailable` among artifacts of non-current states or orphan sources, and
  `s01_discard_none_r1` has no more of them than `s01_discard_sync_r1`. No prediction of how
  many.
- **H5 (descriptive).** Per image and source kind, the share of recovered files with each
  verdict. No prediction: most corpus files are small and inline, which have no data checksum.

**What would refute it.** Any count above zero in H2 or H3, or an H1 failure: then the verdict
cannot feed the Confirmed tier of M6c as designed. H4 failing would mean that on this corpus a
data checksum adds nothing beyond `complete` for stale states, which would be reported as such.

**What it means for the paper.** C4's "csum-tree-verified content": how many recovered files the
image's own checksums can confirm, per source kind, and that a confirmation is never wrong on
the corpus.

## 2. Method

**Images.** Every image of `corpus/manifest.tsv` present on the host that the tool opens (not
`m1_unknown_incompat`, which the gate refuses, and not the superblock-damage variants
`m1_mirror_damage` and `m1_foreign_mirror`, whose data equals `m1_xxhash`'s), and `sandbox.img`.
Each is a fixed image: the counts are deterministic for that image, so one run per image with
the image's SHA-256 before and after (plan.md §7, pure-parse results). Guest builds of the same
recipe give other images; the spread across builds is not measured here (§7).

**Per image.** `catalog build --full-sweep`; `recover --root all --tree all --orphans --logs`.
Counted over artifacts of kind `file` that are not duplicates: per `source_kind` and
`csum_verdict` (NULL counted as `none`); the H1 set (anchored artifacts of the state known as
`current` with at least one `regular` extent read and no NODATASUM flag); for H2 every artifact
whose `sha256` is among the 64-hex-digit tokens of the image's scenario log; for H3 the
artifacts named in the log (`=== FILE`, `=== DOOMED`, the `sha256sum` lines of `s01`, `m1_*`,
`m2_logtree`) with a single logged hash. Also counted: sectors repaired from a mirror,
`tail_rewritten` sectors, csum trees read with a gap.

**Reported.** One table per image and the totals, with the image hashes.

### 6.1 What the numbers say

- **H1 holds.** Every current-state file with checksummed data on disk is `match` on all five
  csum types (crc32c on `m6_datacsum` and `sandbox`, xxhash, sha256, blake2b) and with zlib, LZO
  and zstd compression, except the registered `damaged.txt`.
- **H2 holds:** 0 of 182 artifacts with a logged hash is a `mismatch`. Before the
  `tail_rewritten` rule it was 10 (the fault in the registration); with it, 10 sectors on
  `m4_deep` match only with the bytes past the end of the file zeroed.
- **H3 holds:** 0 of 125 `match` artifacts with a logged name has another hash. The parenthesis
  of §1 was wrong: the victims of `m4_deep` are each written once under their own name, so they
  are counted, not excluded.
- **H4 is refuted as registered**, and the reason is visible in the table: on
  `s01_discard_sync_r1` the stale states are gone with their metadata (2 csum trees against 35
  without discard, EXP-000), so there is no stale file to judge. On `s01_discard_none_r1` the
  stale files of the 33 older states still match their own csum trees: nothing overwrote them.
  The corpus has no image where data of a surviving old state was overwritten in place; only
  the mutated `m6_datacsum_flipped` gives a `mismatch`.
- **H5.** The data checksum decides for few files of this corpus: 183 of 11 626 files are
  `match`, almost all the rest are `no_csum` because the scenarios write small inline files
  (`m3_wide`'s 1 500 files, `m4_deep`'s padding, `m5_delsubvol`'s 300 files). Every log-tree file
  with data on disk is `match` against its own log's EXTENT_CSUM items; 20 lone-leaf files are
  `match` against the oldest state not older than their leaf. No `unavailable` and no
  `partial_match` occurred.
- **A finding.** The oldest state of most images has a csum tree with a gap (its root block was
  reused); the fallback to the current tree then decides, and that is where the rule "a complete
  tree's absence is final" matters.

## 7. Threats to validity

- **Internal.** Not blind (registration). One fault was found and fixed before registration
  (`tail_rewritten`), and the fix is a rule of the kernel's write path, not a threshold tuned to
  the data. One run per image: the counts are deterministic for an image, and were not compared
  across guest builds; another build of a recipe gives other images and other counts.
- **External.** Stock 7.0 guest kernel, virtio disk, 512 MiB images, mostly inline-sized files;
  the share of files a checksum can decide (H5) depends on file sizes and will be far higher on
  real images. No image has overwritten data under a surviving old state (H4).
- **Construct.** `match` says the bytes are the ones checksummed, under a 32-bit crc32c on
  crc32c images (collision chance 2^-32 per sector) and 64-bit or 256-bit sums otherwise. It does
  not say that the checksum tree itself was not forged: a csum tree is trusted as far as its
  tree-block checksums are, like any other tree.

## 8. Status

H1, H2, H3 supported; H4 refuted as registered, for want of an image that exercises it (a
follow-up for M7's corpus: overwrite a file's data in place after a state survives, then read
that state). The verdicts are ready for the M6c tiers.
