# EXP-001 — Checksum-type coverage: legacy prototype vs btrfska

- **Date:** 2026-09-15
- **Milestone:** M1 task 11 (plan.md §5), catalog.md M1c entry
- **Script:** [`experiments/exp001.py`](exp001.py); environment:
  [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-001/` (gitignored): `env.txt`,
  `results.json`, `table.md`, `stdout.txt`, `legacy/<image>/` and
  `legacy/<image>.log`

## 1. Hypothesis

On images checksummed with xxhash64, sha256 or blake2b, the legacy prototype
accepts no tree block and lists no file, because it validates every block with
crc32c (defect #1). btrfska validates every tree block it reaches on all four
checksum types, and lists every file of every root set with bytes identical to
the ground truth. On the crc32c `sandbox.img`, both tools list and recover the
same known files.

## 2. Method

Both tools run on four images that differ in checksum type. Each metric is
defined below; the script docstring holds the full definitions.

- **Tree blocks accepted and rejected.**
  - Legacy scans the image in targeted mode. It accepts a block whose fsid
    matches and whose crc32c validates, and counts `orphan_nodes_found` +
    `current_nodes_scanned`: orphans (generation below the superblock's)
    and current-generation leaves. It does not count current internal
    nodes.
  - Legacy's rejected blocks are `checksum_failures`: fsid-matching blocks
    whose crc32c fails.
  - btrfska walks every tree of every root set: the four backup roots and
    the current state, their slot trees, and every ROOT_ITEM in each root
    tree.
  - btrfska accepts a distinct tree block (logical address) when one
    physical copy passes all twelve node checks, and rejects it otherwise.
  - The two tools discover blocks differently (scan vs anchored walk), so
    their totals are not comparable. The claim tested is acceptance versus
    rejection on each checksum type.
- **Files listed per generation.**
  - Legacy: distinct file names among its `recovered_files`, per generation.
  - btrfska: regular files in every subvolume and snapshot of that
    generation's root set.
- **Distinct files byte-identical to ground truth, out of those listed.**
  - Legacy counts distinct (name, generation) pairs and btrfska distinct
    (subvolume, inode, name) triples.
  - A file counts only if its bytes match every time it is listed. Legacy
    entries marked `(duplicate)` have no output file of their own
    (legacy/utils/btree.py:659-666) and are skipped.
- **Ground truth.**
  - s01 images: the guest-printed SHA-256 for `keep.txt`, `deleted_big.txt`
    and `deleted_inline.txt`, and the scenario script's content for
    `churn_1..6` (`echo genN`).
  - `sandbox.img`: there is no scenario log, so the reference is
    dissect.btrfs 1.10's stream bytes for the same generation. For a backup
    generation, its root tree is swapped for that generation's.
- **Success.** The hypothesis holds if legacy accepts 0 blocks and lists 0
  files on the three non-crc32c images. btrfska must reject 0 blocks and
  match every listed file on all four images, and both tools must recover
  both sandbox files byte-identically.
- **Repetitions.** These are deterministic parses of fixed images, so one run
  suffices (plan.md §7). The script was run with `--runs 2`, which repeats the
  whole measurement, legacy included, and fails unless both runs give
  identical results; they did. No timing is reported.
- **Image integrity.** Every image's SHA-256 is taken before and after its two
  tool runs; the script fails if one changes.

## 7. Threats to validity

- **Internal.**
  - The legacy and btrfska block counts come from different discovery
    methods: a scan that includes orphans, versus anchored walks. Only
    acceptance versus rejection is compared, not totals.
  - Legacy's accepted count omits current-generation internal nodes by
    design.
  - The sandbox reference is dissect.btrfs, not independent ground truth.
    dissect agreed with the guest SHA-256s on all 150 s01 file reads of the
    M1c oracle test, but it validates no checksum.
- **External.**
  - One small image per checksum type. All three s01 images come from the
    same scenario on a stock 7.0 guest kernel with virtio storage and
    btrfs-progs 6.6.3 mkfs.
  - The s01 generations are not bit-stable across regenerations (plan.md
    §7). The counts hold for these image hashes, and a regenerated image
    needs a rerun.
  - Every s01 image is zstd-compressed. Compression coverage (zlib, LZO) is
    measured by the M1c oracle tests, not here.
- **Construct.**
  - "Tree blocks accepted" measures the checksum gate, not the recovery of
    deleted content.
  - The deleted s01 files are reached only through snapshot 257. Neither
    tool is tested here on deleted files that survive only in unreferenced
    blocks; that is M2 and M4.

## 8. Status

**Supports the hypothesis.**
- On the xxhash64, sha256 and blake2b images, legacy accepts 0 tree blocks
  and lists 0 files: the defect #1 regression proof for the M1 DoD.
- btrfska accepts every reached block (23, 25 and 23) and reads all 10
  distinct files byte-identically in all five root sets.
- On crc32c both tools recover the two sandbox files byte-identically.
