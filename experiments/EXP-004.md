# EXP-004 — Old-root discovery against `btrfs-find-root`: where is btrfska new?

- **Date:** 2026-09-21 (registration and results); addenda §6.7 and §6.8 the same day, on new images
- **Milestone:** paper-readiness experiment "E-findroot" (plan.md §8; paper-draft.md §10, gaps G5
  and G9, contribution N5)
- **Script:** [`experiments/exp004.py`](exp004.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-004/` (gitignored): `results.jsonl` (one line per image),
  `findroot/<image>.txt` (the tool's verbatim output), `table.txt`
- **Registration:** §1 and §2 were committed before the script was run on any image. The commit

## 1. Hypothesis

`btrfska roots` reports historical root trees ("states"). `btrfs-find-root`, part of btrfs-progs,
has done something similar since 2011. The paper may claim old-root discovery as new only where
find-root cannot do it, so this experiment asks where that is.

**What find-root does**, read from the source before any run (`btrfs-find-root.c`; btrfs-progs
v6.6.3 and v7.1 differ in one usage string only):
1. It opens the filesystem with the *current* chunk tree (`OPEN_CTREE_CHUNK_ROOT_ONLY`).
2. `btrfs_find_root_search` iterates the **metadata block groups of the current chunk map**
   (`btrfs_next_bg_metadata`) and reads every address `chunk_offset + k × nodesize` through that map
   with `read_tree_block` (checksum, fsid, bytenr; no parent check).
3. Of the blocks whose owner is the wanted tree (default: the root tree, objectid 1), it keeps,
   **per generation, those at the highest level it saw** for that generation
   (`add_eb_to_result`). With `-a` it lists all of them, one "Well block B(gen: G level: L)" line
   each.

**Registered prediction.** Let *I* be the root-tree (owner 1) blocks that `btrfska roots
--full-sweep` indexes on an image. For every image:
- **P1 (find-root is the inside-map subset).** The set of (bytenr, generation, level) that
  `btrfs-find-root -a` prints equals the subset of *I* that (a) the current chunk map places, in a
  METADATA chunk, at a physical offset where btrfska scanned it, (b) lies on a nodesize boundary
  relative to its chunk's start, and (c) has the highest level among the blocks of its generation
  that satisfy (a) and (b).
- **P2 (nothing outside the map).** find-root prints no block that only a removed chunk placed:
  every state whose root-tree block lies outside the current chunk map is absent from its output.
- **P3 (no novelty inside the map).** Every btrfska state whose root-tree block the current chunk
  map places is also in find-root's output. Inside the current chunk map btrfska finds no root
  tree that find-root misses.

**What would refute it.** A block printed by find-root that btrfska does not index (btrfska missed
a valid root-tree block, or validates more strictly); an inside-map state that find-root does not
print (then discovery is new inside the map as well, or find-root validates more strictly); or a
block outside the map in find-root's output (then I misread its scan range).

**What the outcome means for the paper.** If P1–P3 hold, the claim is narrowed to: *discovery of
root trees outside the current chunk map* (after balance, reclaim or chunk removal), plus what
btrfska adds to any root it finds (every physical copy validated, completeness, failure classes,
forgery-resistant candidates, all four checksum types). "Finds older roots than the backups" is
then **not** claimable, because find-root already does that inside the map.

## 2. Method

**Images.** Every image of `corpus/manifest.tsv` as built by `corpus/build.py` on this host (14),
plus `sandbox.img`. `sandbox.img` is never handed to a foreign tool: find-root runs on a sparse
copy of every image under `images/scratch/exp/EXP-004/copies/`, and the copy's SHA-256 is taken
before and after to record whether find-root wrote to it.

**find-root.** `corpus/vm/pinned.sh btrfs-find-root -a COPY` (btrfs-progs 6.6.3 from
`corpus/vm/guest.lock`, so the result does not depend on the host's btrfs-progs). Exit status,
stdout and stderr are kept verbatim. "Well block" and "Found tree root" lines are parsed into
(bytenr, generation, level). An image find-root cannot open is recorded as such.

**btrfska.** `discover_image(img, fs, full_sweep=True)` through the Python API, the same code path
as `btrfska roots --full-sweep`. From its block index, every owner-1 block gives (bytenr,
generation, level), its physical copies, whether the current chunk map places it at one of those
copies and in which chunk type, its alignment to the chunk start, and whether it is a state
(candidate root-tree block), with the state's completeness. An image btrfska refuses at the
feature gate is recorded as such and not compared.

**Comparison, per image.** The predicted find-root set (P1) is computed from btrfska's index and
compared with the parsed find-root set: equal or not, and the members of each difference. States
are split by placement (inside or outside the current chunk map) and counted as found or not
found by find-root (P2, P3).

**Repetitions.** Both tools parse a fixed image deterministically, so each image is measured once
(plan.md §7). The images themselves come from one build on one host; §7 says what that limits.

### 6.2 The registered predictions

- **P1 holds on 13 of 13 compared images.** The blocks find-root printed are exactly the root-tree
  blocks btrfska indexed that the current chunk map places in a METADATA chunk, on the nodesize
  grid, at the highest level of their generation. No block was printed that btrfska had not
  indexed, and none was predicted that find-root did not print.
- **P2 holds.** Of the 133 states whose root-tree block lies outside the current chunk map,
  find-root printed 0.
- **P3 holds.** Of the 229 states inside the current chunk map, find-root printed 229. **Inside the
  current chunk map, btrfska's discovery found no root tree that find-root misses.**

On the s01-type images (final generation 38 in this build) find-root reaches generations 17–38,
that is the four backup generations 35–38 and 18 older ones; btrfska adds generations 3–16, the
states written before the scenario's final balance moved every chunk. On `sandbox.img` (generation
14) both find the four backup generations 11–14 and btrfska adds the generation-3 state. On
`m2_logtree` (generation 8) both find four root-tree blocks of generations 6–8, three of them
backup roots, and btrfska adds the generation-3 state. Under `discard=sync` one state survives inside the map and one
outside; each tool finds what its range allows.

### 6.3 Images that could not be compared

- `m1_unknown_incompat.img`: both tools refuse it. find-root: "couldn't open because of unsupported
  option features (10000000000)"; btrfska: `UNSUPPORTED_INCOMPAT UNKNOWN_BIT_40`.
- `m1_mirror_damage.img` (primary superblock zeroed): **find-root cannot open it** ("No valid Btrfs
  found"); btrfska selects a valid superblock mirror and reports 35 states, 22 inside and 13
  outside the map, the same as on the undamaged `m1_xxhash.img` it was derived from. This is a
  difference in robustness, not in discovery, and rests on one image.

### 6.4 Side result: find-root is read-only here

The copy handed to find-root had the same SHA-256 before and after on 15 of 15 images.

### 6.5 What the numbers show

1. **find-root already finds root trees older than the four backup roots** whenever they lie in a
   metadata chunk of the current chunk map: 18 generations beyond the backups on every s01-type
   image. "Discovers historical roots beyond the backup roots" is therefore **not** new and must
   not be claimed.
2. **What is new is the range.** Every state btrfska finds and find-root does not is outside the
   current chunk map: 133 of 133. find-root cannot reach them by construction, because it
   enumerates block groups of the current chunk tree and reads through the current map. btrfska
   scans the unmapped gaps physically and resolves those states through their own chunk items.
3. For any root both tools find, btrfska still reports more about it: every physical copy
   validated separately, the trees the state names, completeness, and why a missing block is
   missing. find-root prints an address, a generation and a level. That is a difference in the
   record produced, not in discovery, and this experiment does not measure its value.

### 6.6 What the numbers do not show

- Whether the outside-map states are *useful*. A state found is not a file recovered; that is
  experiment E-rec (plan.md §8). On these images the outside states are complete (completeness 1.0)
  except generation 3, the mkfs-era state: 0.83 on every corpus image, 1.0 on `sandbox.img`.
- How often states outside the map exist in practice. Here they exist because scenario s01 ends
  with a full balance on a young filesystem and nothing reuses the freed chunks (EXP-002 §6.5).
  An aged filesystem, or one that never relocated a chunk, may have none.
- Behaviour when a root tree has more than one block. Every root tree in these fifteen images is a
  single leaf, so rule (c) of P1 (highest level per generation) and btrfska's "no parent
  references it" rule select the same blocks. §6.7 adds an image with a two-level root tree, where
  they still do. What remains untested is a root-tree leaf whose parent node was lost: find-root
  keeps only the top level it sees per generation, while btrfska reports such a leaf as a state of
  its own, so the two sets could differ inside the map.

### 6.8 Addendum: a deep history, and a root-tree leaf whose parent is lost (2026-09-21)

§6.7 left one case untested: a root-tree leaf whose parent node was lost. Two images were added
for M4 (catalog.md, M4e):
- `m4_deep`: 48 subvolumes (a two-level root tree), about 90 generations, no balance;
- `m4_deep_lost_parent`: `m4_deep` with one byte inverted in every physical copy of its oldest
  root-tree node that has a child no other root-tree node points to (`corpus/mutate.py
  lose-root-node`; checksums left stale, as for `m1_badnode_both`). On the dev host's build that
  is the generation-17 node, and the child is a generation-17 leaf.

**Registered before `exp004.py` was run on either image** (this subsection's text up to
"Results" is in the commit that adds the images; the results come in a later commit). Only
btrfska had been run on trial builds of `m4_deep`, to develop the scenario; find-root on neither.

- The registered predictions **P1, P2 and P3 apply unchanged** to both images.
- On `m4_deep` I expect no root-tree leaf without a parent: trial builds had none. The allocator
  places a generation's blocks side by side, so a node and its leaves are overwritten together.
- **P4 (the lost parent).** Let G be the generation of the corrupted node.
  - btrfska: the node fails its checksum, is not indexed and is no longer a state. Each child
    that no other root-tree node points to becomes a state of level 0. It names only the trees
    whose ROOT_ITEMs lie in that leaf, so it stands for part of a root tree, and its completeness
    says nothing about the rest.
  - find-root: `read_tree_block` rejects the node, so the highest level it sees for generation G
    is 0, and it prints **every** generation-G root-tree leaf it can read: the orphaned one, and
    also any generation-G leaf that a node of another generation still points to, which btrfska
    does not call a state because it is referenced. P1 predicts exactly that set, since rule (c)
    is taken over the blocks btrfska indexes. P3 holds for the orphaned leaf: it is a btrfska
    state inside the map, and find-root prints it.
- **What would refute it.** find-root printing the corrupted node (then it validates less than
  §1 says); find-root not printing the orphaned leaf (then "highest level per generation" is not
  what it does when a node is unreadable); or btrfska not listing the orphaned leaf as a state.

  find-root printed the 77 nodes and one leaf, 32374784 of generation 7, and not the
  generation-3 state. That leaf is the only root-tree block of generation 7 on the image, so it

## 7. Threats to validity

- **Internal.** One build of each image on one host; both tools are deterministic on a fixed image,
  so repetition would not change a row, but a different build shifts generation numbers (on a
  slower CI runner the same scenario ended at generation 39, catalog.md 2026-09-21). The claims
  above are about set relations per image, which do not depend on those numbers. "Inside the map"
  is computed by btrfska's own chunk map; a bug there would bias P1, but P1 is checked against an
  independent tool's output and matched on every image.
- **External.** Small (256–512 MiB), young, single-device, DUP-metadata filesystems, one scenario
  family, single-leaf root trees, crc32c/xxhash/sha256/blake2b checksums but no RAID profile, no
  MIXED_GROUPS, no multi-device. find-root was run with its default owner (the root tree) only;
  `-o` for other trees was not compared.
- **Construct.** "State found" counts a root-tree block, not recovered evidence. The comparison
  credits find-root with every block it prints, including the ones it marks "generation/level
  doesn't match", because that is the list an examiner would work from.
