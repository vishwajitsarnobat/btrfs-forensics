# EXP-015 — Reachability classes against "generation below the superblock" on `sandbox.img`

- **Date:** 2026-10-07
- **Milestone:** paper readiness, gap G13 (`docs/paper-draft.md`); the measurement behind
  "sandbox 71 = 8 + 34 + 28 + 1" (paper-draft §6.5, N9, F3, traceability row 11) and the M2a
  reconciliation table in catalog.md
- **Script:** [`experiments/exp015.py`](exp015.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-015/results.json` (gitignored)
- **Registration:** not blind. The reconciliation was first made in M2a and is asserted by
  `tests/test_scan_classify.py`; this record turns it into a table with every disagreeing block
  listed. The prediction written before the run: the M2a numbers come back unchanged (71 legacy
  orphans = 8 live + 34 backup-reachable + 28 unreferenced + 1 invalid; 2 current-generation
  orphans outside the legacy definition), because a scan of a fixed image is deterministic.

## 1. Hypothesis

The prototype's orphan definition (a nodesize-aligned tree block whose checksum validates and
whose generation is below the superblock's, `legacy/utils/btree.py:472-517` at tag
`legacy-final`) is wrong in both directions: it counts live blocks that have simply not changed
since an older generation, and it misses orphans written in the current generation. Registered:
on `sandbox.img` both kinds of disagreement occur, and every block the two definitions disagree
on is explained by one of three causes: unchanged live block, current-generation orphan, or a
check the prototype does not make.

**What would refute it.** A disagreeing block with none of those three explanations; or no
disagreement at all, in which case generation would be a usable proxy for reachability on this
image.

**What it means for the paper.** N9 and F3: "generation below the superblock" is neither "orphan"
nor "deleted", so a count of orphans must say which definition it uses (paper-draft glossary,
"legacy-compatible orphan").

## 2. Method

One scan of the image (`scan.classify.scan_image`, targeted regions), and the same with a full
sweep as a check; both must give the same table and the same blocks. Every candidate tree block
gets two labels:
- its reachability class (`scan/classify.py`): `live` (reached from the current state),
  `backup_reachable` (reached only from a backup root), `unreferenced` (from neither) or
  `invalid` (fails a check). The orphans are the middle two;
- the flag `legacy_orphan`: the prototype's definition above.

A block is a *disagreement* when exactly one of the two definitions calls it an orphan. Each one
is listed with its physical offset, logical address (bytenr), generation, owner, level, whether
it lies outside the current chunk map, and the checks it fails. The image's SHA-256 is taken
before and after.

## 3. Image / scenario

`sandbox.img`, the fixed fixture of the repository (not rebuilt; its hash is pinned in
`tests/fixtures/SHA256SUMS`): crc32c, nodesize 16 KiB, superblock generation 14, SHA-256
`07ca38d42b11062f5461f97a572134a1b56cbf94e1138183d6e74502f5876418`, unchanged by the run. A scan
of a fixed image is deterministic, so one run is the measurement (plan.md §7, "pure-parse
results on a fixed image").

- **The hypothesis holds.** Both directions occur: 8 live copies (4 blocks × 2 DUP copies) are
  legacy orphans only because they have not changed since an older generation, and 2
  current-generation copies (1 block × 2) are orphans the generation rule cannot see, because a
  block already written in the running transaction is copied again on its next change
  (`should_cow_block`, ctree.c:621-625, read from source). The eleventh is a check the prototype
  does not make.
- **The numbers equal the documents.** 71 = 8 + 34 + 28 + 1, 21 legacy orphans outside the map
  (20 unreferenced + the invalid leaf), 2 current-generation orphans missed, 34 of 64 orphans
  backup-reachable: catalog.md M2a and paper-draft.md (§6.5, N9, F2, F3, rows 11 and 24) agree.

## 7. Threats to validity

- **Internal.** Reachability is as complete as the walks: a block counted `unreferenced` could be
  reachable from a tree the walks do not know. The extent-tree cross-check agrees with the live
  set exactly on this image (`extent_tree_only` 0, `walk_only` 0; `tests/test_scan_classify.py`),
  which makes a missed live block unlikely.
- **External.** One small image (85 candidates), built by hand, no balance, no discard. The kinds
  of disagreement are general (they follow from copy-on-write rules), but their counts are not:
  EXP-002 §6.1 gives the same split on the s01 images (355 stale = 10 live + 24 backup-reachable
  + 316 unreferenced + 5 invalid).
- **Construct.** `legacy_orphan` reimplements the prototype's rule; its parity with the
  prototype is asserted on this image offset by offset against the prototype's own output
  (`tests/ground_truth/sandbox_legacy_scan.json`, `test_sandbox_legacy_compatible_orphans_are_the_legacy_offsets`).

## 8. Status

**Supports** the hypothesis. What the paper may say, on this image: the prototype's 71
generation-defined orphans are 8 live + 34 backup-reachable + 28 unreferenced + 1 invalid, and the
generation rule misses 2 current-generation orphan copies; generation below the superblock is
therefore neither "orphan" nor "deleted". The mechanism of the missed copies is read from source,
not measured. Follow-up: the same table on the M7 images.
