# EXP-016 — btrfska's file reads against dissect.btrfs, per image and compression codec

- **Date:** 2026-10-07
- **Milestone:** paper readiness, gap G13 (`docs/paper-draft.md`); the measurement behind "152 of
  152 oracle file reads" (paper-draft N1, §6.5, traceability row 2; catalog.md M1c "Oracle
  results"), extended from four images to the whole corpus
- **Script:** [`experiments/exp016.py`](exp016.py); the same comparison as
  [`tests/oracle/test_file_parity.py`](../tests/oracle/test_file_parity.py), reported instead of
  asserted; environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-016/results.jsonl` (gitignored), one line per image
- **Registration:** partly blind. On the four images of the M1c claim the result was known (the
  oracle tests assert it); the prediction was that it comes back unchanged. On the other 17 images
  nothing had been compared before, except that a trial run of the script on the first ten
  manifest images, made while writing it, showed `m1_mirror_damage` failing in dissect. The
  prediction for the rest, written before the full run: every read btrfska completes equals
  dissect's bytes, and every image where dissect fails or a listing differs has a cause that is
  not a byte difference.

## 1. Hypothesis

btrfska reads every regular file of every root set the same as dissect.btrfs 1.10, an independent
implementation, whatever the compression codec (none, zlib, LZO, zstd) and the checksum type, and
equal to the guest's SHA-256s where the scenario logged them. Registered: 0 byte differences on
every image; on the four images of the M1c claim, 152 of 152 reads equal and 150 of 150 equal to
the expected hashes.

**What would refute it.** Any read where both tools return bytes and the bytes differ; a read
btrfska completes that differs from a logged SHA-256.

**What it means for the paper.** N1: btrfska's validated read path does not cost correctness on
the bytes. Agreement with dissect is not proof of correctness (both could share a misreading), but
the guest hashes are independent of both.

## 2. Method

For every image, every root set (the four backup roots by generation, then the current state;
fewer where a backup root tree fails validation), every subvolume and snapshot the root set's root
tree names, and every regular file btrfska inventories there, one read:
- btrfska: `extents.read_file`, counted only when complete;
- dissect.btrfs: the inode's stream. dissect reads the current root tree only, so for a backup root
  set its root tree is swapped for that set's (`Btrfs._root_tree`, a private attribute, as in the
  test) and its tree cache cleared;
- expected: the SHA-256 the guest printed, or the content the scenario script fixes, on the images
  built by the s01 scenario (`m1_xxhash`, `m1_sha256_bgt`, `m1_blake2b`, `m1_lzo`, `m1_zlib`, the
  three `s01_discard_*`). Other scenario logs name files ambiguously and mutated images have no
  log, so they get no expected hash.

A read is `equal`, `differ`, `dissect failed` (dissect could not open or read it) or `btrfska
incomplete`. A file's codec is the set of compression types of its extents (`none` if none is
compressed). dissect's own directory walk of each subvolume is compared with btrfska's inventory
as a check, and problems (a root tree or subvolume tree btrfska rejects, dissect failing to open)
are listed.

## 3. Image / scenario

`sandbox.img` (fixed fixture, SHA-256 `07ca38d4…`) and the 20 rows of `corpus/manifest.tsv` as
built on this host by `./setup.sh` (pinned mkfs.btrfs 6.6.3, guest kernel 7.0.0-31). The corpus
images come from guest runs, and a rebuild gives a new instance (new UUIDs and hashes); the four
images of the M1c claim gave the same counts here as on the earlier build M1c used, but that is
two builds, not a measured spread. Reading a fixed image is deterministic, so one run per image is
the measurement. SHA-256s of the four claimed images are in §4.

btrfska completed every read it attempted. "Distinct files" counts (subvolume, inode, content)

**Where something other than "equal" happened, and why:**
- `m1_mirror_damage` (primary superblock zeroed): dissect raises `Invalid btrfs superblock` on
  every root set. It reads mirror 0 only, as the kernel does; btrfska falls back to mirror 1
  (EXP-017) and reads all 50.
- `m1_badnode_both` (one leaf corrupted in both DUP copies): btrfska rejects subvolume 256's tree
  in every root set (`IncompleteTree`, checksum mismatch on both copies) and reads nothing from
  it; the 15 reads are snapshot 257's 3 files in 5 root sets. dissect was not asked to read
  subvolume 256: whether it would return bytes from the corrupted leaf is not measured here.
- `m2_logtree`: the oldest backup root tree (generation 5) fails validation, its block rewritten
  after the backup slot was written (owner 10, generation 7: the `reused` case of
  research.md §10.11), so 4 root sets.
- `s01_discard_sync_r1`: three backup root trees were discarded (all-zero blocks), so 2 root
  sets.
- `m4_deep`, `m4_deep_lost_parent`: dissect's directory walk misses inode 707 in subvolume 5 in
  the last backup and the current state. It is `open_unlinked.txt`, unlinked while open (it has
  an ORPHAN_ITEM and no directory entry); btrfska inventories it by inode, and dissect reads it by
  inode number with the same bytes, which are the SHA-256 the guest logged
  (`23f90f8b…`, `=== ORPHAN` line of `m4_deep.log`).

- **The hypothesis holds.** No read differs, on any image, codec or checksum type; every expected
  hash (370) matches.
- **The number equals the documents.** 152 reads on the four claimed images, all equal, 150 with
  guest or script hashes, all equal: catalog.md M1c and paper-draft.md N1, §6.5 and row 2 agree.
- **Coverage of codecs.** zstd and none on many images; LZO and zlib on one image each (50 reads
  each, 10 distinct files).

## 7. Threats to validity

- **Internal.** dissect is used through a private attribute for backup root sets; a mistake there
  would show as differences, not hide them, unless both tools read the same wrong tree, which the
  guest hashes exclude where they exist. Equality with dissect is evidence of agreement, not of
  correctness, on the 24 841 reads without an expected hash.
- **External.** Small scenario images; most files are tiny and many are inline. LZO and zlib are
  each on one image only. No RAID profile other than DUP metadata, no multi-device image.
- **Construct.** Only files btrfska inventories are compared, so a file btrfska misses entirely is
  caught only by the directory-walk check (which found no such file); files reachable only through
  orphan nodes or log trees are out of scope (EXP-006, EXP-008).

## 8. Status

**Supports** the hypothesis. What the paper may say: on 21 images (four checksum types, four
codecs), all 25 211 regular-file reads btrfska makes across the backup and current root sets equal
dissect.btrfs's bytes wherever dissect can read them (25 161; dissect cannot open the image with a
zeroed primary superblock), and all 370 reads with a guest or script SHA-256 match it; the
paper's "152 of 152" is the four-image subset. Follow-ups: a dissect read of the corrupted
subvolume of `m1_badnode_both` (what dissect returns where btrfska refuses, part of N1's
comparison, gap G13); LZO and zlib on more images (M7).
