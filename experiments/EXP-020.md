# EXP-020 — Confidence tiers of recovered files, per source, against the scenarios' logs

- **Date:** 2026-10-07 (registration, then results the same day)
- **Milestone:** M6c (plan.md "M6c: confidence tiers for every artifact"); claim C4
  (evidence-rule-derived confidence tiers), the calibration experiment E-tiers of plan.md §8
- **Script:** [`experiments/exp020.py`](exp020.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-020/results.jsonl` (gitignored), one line per image
- **Registration:** §1 and §2 were committed before the tiers were implemented, so before any
  tier was computed on any image. The verdicts the tiers read (`csum_verdict` of M6a, EXP-013;
  the `missing` reasons of M5c) were known from EXP-013 and EXP-008 when the predictions were
  written.

## 1. Hypothesis

The tier rules of plan.md M6c put a recovered file in `confirmed` only when its content is the
content the scenario wrote: on the corpus, `confirmed` is never wrong, and the tiers order the
files by how often they are right.

- **H1 (Confirmed is never wrong).** Every `confirmed` file (artifact of kind `file`, not a
  duplicate) whose name the scenario logged has a SHA-256 among the hashes logged for that name,
  on every image and every source kind. Registered: 0 wrong.
- **H2 (current files with checksummed data are Confirmed).** On every image, every file of the
  current state (`anchored_root` of the state the superblock names) that has data on disk and
  data checksums is `confirmed`, except `damaged.txt` of `m6_datacsum_flipped`, which is
  `unattached` (`csum_mismatch`); the nodatasum file of `m6_datacsum` is `probable`. No artifact
  of any image fires `backref_disagrees`: a committed state's extent tree back-references every
  extent its file trees point to, so a disagreement on an honest image would be a fault of the
  rule.
- **H3 (orphans are not Confirmed on structure alone).** No `orphan_node` or `orphan_graph` file
  is `confirmed` unless both `csum_match` and `backref_attributed` fired (true by construction;
  checked), and at most as many are `confirmed` as EXP-013 found `match` among lone-leaf files
  (20 over its 20 images; the images added here, `m5_reuse*` and `m6_*`, are not bounded by it).
- **H4 (the tiers are ordered).** Over all images, among files with a logged name, the share
  whose SHA-256 is a logged hash for the name is highest for `confirmed`, lower for `probable`,
  lowest for `unattached` (a file that is not `complete` has no hash and counts as not right).
- **H5 (descriptive).** Tiers per source kind and the rules that fired most. Expected without a
  number: `anchored_root` mostly `confirmed` (most corpus files are inline, which `content_in_leaf`
  proves), `orphan_node` mostly `probable` (inline content of leaves no commit vouches for),
  `log_tree` `probable`.

**What would refute it.** H1 above zero: the rules can confirm a wrong file and C4 cannot claim
calibrated tiers as they stand. H2 failing (a current file with checksummed data not
`confirmed`, or any `backref_disagrees`): a rule contradicts honest evidence. H4 failing: the
middle tier does not mean what its name says on this corpus, which would be reported as such.

**What it means for the paper.** Abstract B's "[Z] % of Confirmed artifacts are correct", and how
many recovered files of each source a tier can vouch for.

## 2. Method

**Images.** Every image of `corpus/manifest.tsv` present on the host that the tool opens, except
`m1_mirror_damage` and `m1_foreign_mirror`, whose data equals `m1_xxhash`'s (superblock damage
only), and `m1_unknown_incompat`, which the gate refuses; and `sandbox.img`. Each is a fixed
image: the counts are deterministic for that image, so one run per image with the image's SHA-256
before and after (plan.md §7, pure-parse results). Guest builds of the same recipe give other
images; the spread across builds is not measured here.

**Per image.** `catalog build --full-sweep`; `recover --root all --tree all --graph --logs` (every
source kind: anchored roots, ORPHAN_ITEM inodes, fragments and joined leaves, lone leaves, log
trees). Counted over artifacts of kind `file` that are not duplicates: per `source_kind` and
`tier`, and per rule. Also over every artifact (directories and symlinks included) per tier.

**Ground truth.** The scenario's log (a derived image uses the log of the image it was made from,
as in EXP-013): every `=== FILE`, `=== DOOMED`, `=== VICTIM`, `=== FLASH`, `=== ORPHAN` line and
every `sha256sum` line `HASH  /mnt/PATH` gives a hash for a file name (the last path component).
A file is *evaluated* when its name has at least one logged hash; it is *right* when it is
`complete` and its SHA-256 is one of the hashes logged for its name. A name logged with several
hashes (a file written more than once) accepts any of them: the log does not say which version
each state held (§7).

**Checks.** H1: evaluated `confirmed` files that are not right. H2: anchored files of the current
state with at least one `regular` extent read and no NODATASUM flag, and their tiers; the count of
artifacts with `backref_disagrees`. H3: `orphan_node` and `orphan_graph` files that are
`confirmed`, and their rules. H4: right / evaluated per tier.

**Reported.** Tiers per source kind for all images together and per image; the checks per image;
the image hashes.

### 6.1 What the numbers say

- **H1 is refuted as registered: 37 of 240 evaluated `confirmed` files have a hash the log does
  not hold.** None was shown wrong. Each is a version of the file the log never hashed: a
  scenario hashes a file once, after writing it, while a committed state can hold it earlier.
  The script classifies them (`explain`), and the three it leaves were checked by hand:
  - 28 are **empty versions**: the file was created and a state committed before its data was
    written (on the `s01`-scenario images, generation 7 holds `keep.txt`, `deleted_big.txt` and
    `deleted_inline.txt` at size 0, generation 8 with the logged content; `m2_logtree`'s
    `committed.txt` likewise);
  - 6 are **prefixes of a logged version**: their bytes are the start of a recovered file whose
    hash the log holds, from a commit in the middle of the write (4 MiB pieces of `m5_reuse`'s
    `a.bin`, `b.bin`, `c.bin`, `w.bin`, and of `m5_reuse_same`'s `c.bin`);
  - 2 are **whole versions of a file the log never hashes**: `big.txt` of `m6_fsid_u` and
    `m6_fsid_m` is the second life's `sv/big.txt`; the scenario hashes only `snap/big.txt`, which
    stays the first life's (the second life's snapshot fails: `snap` exists). Regenerating the
    content as the scenario writes it (`seq 1 30000 | sed "s/^/FSID /"` with the second life's
    fsid, `a8efe144-…` and `e06413b0-…`) gives exactly the recovered hashes;
  - 1 cannot be checked: a 4 MiB version of `m5_reuse_same`'s `z.bin` (random bytes, deleted, its
    chunk removed, so no whole version with a logged hash is recovered to compare it with). It is
    `csum_match` in its own state's csum tree, with `backref_agrees`.

  The metric of §2 cannot tell an unlogged version from a wrong one; the registration did not
  foresee that, and the result stands as it came out. Set aside the 36 explained versions and
  203 of 204 are right, the last one unverifiable.
- **H2 holds.** On every image every current file with checksummed data on disk is `confirmed`,
  except the registered `damaged.txt` (`unattached`, `csum_mismatch`); the nodatasum file of
  `m6_datacsum` is `probable` (`csum_no_csum`). **No artifact of any image fires
  `backref_disagrees`**: where the extent tree of an anchored file's own state was read without a
  gap, it back-references every data extent the file read (182 `backref_agrees`).
- **H3 holds.** 8 lone-leaf files are `confirmed` (the same 4 `separator_flash_*` files on
  `m4_deep` and on `m4_deep_lost_parent`), each with `csum_match` and `backref_attributed`; EXP-013's
  bound was 20. No `orphan_graph` file is `confirmed`.
- **H4 holds**: 85 % of evaluated `confirmed` files are right, 11 % of `probable`, 2 % of
  `unattached`. Most evaluated `probable` and `unattached` files are log-tree versions of
  `m5_reuse*` in the middle of a write (unlogged prefixes again) and fragment versions with
  `inode_item_older_than_extent`.
- **H5.** Anchored files are almost all `confirmed`, 98 % of them on `content_in_leaf`: the
  scenarios write small inline files. `orphan_graph` files are mostly `unattached` (1 826 of
  2 376): a version written within a transaction often has data newer than its inode item. Log
  files are `probable` when their data matches the log's own checksums or is inline.
- **A finding.** `m5_reuse` and `m5_reuse_same`, built after EXP-013, are the images its H4
  lacked: 53 of their files are `csum_mismatch` (versions of older states and logs whose bytes
  were overwritten after the address range was reused), and every one is `unattached`.

## 7. Threats to validity

- **Internal.** One run per image; the counts are deterministic for an image and were not
  compared across guest builds. The registration was blind to the tiers (§1) but not to the
  verdicts they read. The classification of H1 misses (`explain`) was added after the first run
  showed them; it explains, it changes no tier, and the three cases it leaves were checked by
  hand.
- **External.** Stock 7.0 guest kernel, virtio disk, 512 MiB images, mostly inline-sized files:
  98 % of the `confirmed` files rest on the leaf checksum, not a data checksum. On real images
  with larger files the share proven by `csum_match` will be higher, and so will the share of data
  without a checksum (nodatasum, or a csum tree with a gap).
- **Construct.** `confirmed` rests on checksums: crc32c is 32 bits (collision chance 2^-32 per
  sector or leaf); a csum tree or extent tree is trusted as far as its blocks' checksums are, so
  a forger who rewrites leaves with valid checksums is not caught by these rules (hiding
  detection, M6). The ground truth hashes one version per file, so H1's metric undercounts right
  `confirmed` files (§6.1).

## 8. Status

H2, H3 and H4 supported. H1 refuted as registered (37 of 240 `confirmed` files have no logged
hash), with none of the 37 shown wrong: 36 are versions the log never hashed (empty, a prefix of a
logged version, or a whole unlogged file regenerated from the scenario) and one cannot be checked.
Follow-ups for M7: a ground truth with one hash per committed version, and images with larger
files, so that data checksums rather than leaf checksums carry the `confirmed` tier.
