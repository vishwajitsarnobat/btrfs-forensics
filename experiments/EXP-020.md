# EXP-020 — Confidence tiers of recovered files, per source, against the scenarios' logs

- **Date:** 2026-10-07 (registration)
- **Milestone:** M6c (plan.md "M6c: confidence tiers for every artifact"); claim C4
  (evidence-rule-derived confidence tiers), the calibration experiment E-tiers of plan.md §8
- **Script:** [`experiments/exp020.py`](exp020.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-020/results.jsonl` (gitignored), one line per image
- **Registration:** §1 and §2 were committed before the tiers were implemented, so before any
  tier was computed on any image. The verdicts the tiers read (`csum_verdict` of M6a, EXP-013;
  the `missing` reasons of M5c) were known from EXP-013 and EXP-008 when the predictions were
  written.

## 1. Hypothesis

The tier rules of plan.md M6c put a recovered file in `confirmed` only when its content is the
content the scenario wrote: on the corpus, `confirmed` is never wrong, and the tiers order the
files by how often they are right.

- **H1 (Confirmed is never wrong).** Every `confirmed` file (artifact of kind `file`, not a
  duplicate) whose name the scenario logged has a SHA-256 among the hashes logged for that name,
  on every image and every source kind. Registered: 0 wrong.
- **H2 (current files with checksummed data are Confirmed).** On every image, every file of the
  current state (`anchored_root` of the state the superblock names) that has data on disk and
  data checksums is `confirmed`, except `damaged.txt` of `m6_datacsum_flipped`, which is
  `unattached` (`csum_mismatch`); the nodatasum file of `m6_datacsum` is `probable`. No artifact
  of any image fires `backref_disagrees`: a committed state's extent tree back-references every
  extent its file trees point to, so a disagreement on an honest image would be a fault of the
  rule.
- **H3 (orphans are not Confirmed on structure alone).** No `orphan_node` or `orphan_graph` file
  is `confirmed` unless both `csum_match` and `backref_attributed` fired (true by construction;
  checked), and at most as many are `confirmed` as EXP-013 found `match` among lone-leaf files
  (20 over its 20 images; the images added here, `m5_reuse*` and `m6_*`, are not bounded by it).
- **H4 (the tiers are ordered).** Over all images, among files with a logged name, the share
  whose SHA-256 is a logged hash for the name is highest for `confirmed`, lower for `probable`,
  lowest for `unattached` (a file that is not `complete` has no hash and counts as not right).
- **H5 (descriptive).** Tiers per source kind and the rules that fired most. Expected without a
  number: `anchored_root` mostly `confirmed` (most corpus files are inline, which `content_in_leaf`
  proves), `orphan_node` mostly `probable` (inline content of leaves no commit vouches for),
  `log_tree` `probable`.

**What would refute it.** H1 above zero: the rules can confirm a wrong file and C4 cannot claim
calibrated tiers as they stand. H2 failing (a current file with checksummed data not
`confirmed`, or any `backref_disagrees`): a rule contradicts honest evidence. H4 failing: the
middle tier does not mean what its name says on this corpus, which would be reported as such.

**What it means for the paper.** Abstract B's "[Z] % of Confirmed artifacts are correct", and how
many recovered files of each source a tier can vouch for.

## 2. Method

**Images.** Every image of `corpus/manifest.tsv` present on the host that the tool opens, except
`m1_mirror_damage` and `m1_foreign_mirror`, whose data equals `m1_xxhash`'s (superblock damage
only), and `m1_unknown_incompat`, which the gate refuses; and `sandbox.img`. Each is a fixed
image: the counts are deterministic for that image, so one run per image with the image's SHA-256
before and after (plan.md §7, pure-parse results). Guest builds of the same recipe give other
images; the spread across builds is not measured here.

**Per image.** `catalog build --full-sweep`; `recover --root all --tree all --graph --logs` (every
source kind: anchored roots, ORPHAN_ITEM inodes, fragments and joined leaves, lone leaves, log
trees). Counted over artifacts of kind `file` that are not duplicates: per `source_kind` and
`tier`, and per rule. Also over every artifact (directories and symlinks included) per tier.

**Ground truth.** The scenario's log (a derived image uses the log of the image it was made from,
as in EXP-013): every `=== FILE`, `=== DOOMED`, `=== VICTIM`, `=== FLASH`, `=== ORPHAN` line and
every `sha256sum` line `HASH  /mnt/PATH` gives a hash for a file name (the last path component).
A file is *evaluated* when its name has at least one logged hash; it is *right* when it is
`complete` and its SHA-256 is one of the hashes logged for its name. A name logged with several
hashes (a file written more than once) accepts any of them: the log does not say which version
each state held (§7).

**Checks.** H1: evaluated `confirmed` files that are not right. H2: anchored files of the current
state with at least one `regular` extent read and no NODATASUM flag, and their tiers; the count of
artifacts with `backref_disagrees`. H3: `orphan_node` and `orphan_graph` files that are
`confirmed`, and their rules. H4: right / evaluated per tier.

**Reported.** Tiers per source kind for all images together and per image; the checks per image;
the image hashes.
