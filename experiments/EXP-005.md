# EXP-005 — Does copy-on-write zero node slack? What slack holds, and whether C1 may use it

- **Date:** 2026-09-21 (registration)
- **Milestone:** M4, first item (plan.md M4 "Settle whether copy-on-write zeroes node slack");
  claim C1 of the paper draft; open question 4 of research.md §10.13
- **Script:** [`experiments/exp005.py`](exp005.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-005/` (gitignored): `results.jsonl` (one line per image),
  `table.txt`
- **Registration:** §1 and §2 were committed before the script existed and before the slack of
  any block of any image was looked at. The commit that adds §6 comes after it in the history.

## 1. Hypothesis

Claim C1 names three recovery sources inside a tree block: items beyond `nritems`, node slack, and
the kernel's ORPHAN_ITEM. The first two live in the block's **slack**: the bytes no current item or
key pointer uses.

- Internal node: everything after the last key pointer, `[101 + 33 × nritems, nodesize)`.
- Leaf: the gap between the item array, which grows up from the header, and the item data, which
  grows down from the end of the block: `[101 + 25 × nritems, 101 + offset of the last item's
  data)`; the whole block after the header when `nritems` is 0.

Toolan & Humphries 2026 hid a message in internal-node slack and lost it: "the slack space is not
copied ... slack space is overwritten by zeros at each copy". They say nothing about leaves. The
prototype (`legacy/utils/btree.py`) mines both kinds of slack, after Bhat & Wani 2018.

**What the kernel does**, read at tag v7.0 before any measurement:

1. **Copy-on-write copies the whole block, slack included.** `btrfs_cow_block`
   (`fs/btrfs/ctree.c:646`) hands the work to `btrfs_force_cow_block` (`ctree.c:464`), which
   allocates the new block and calls `copy_extent_buffer_full(cow, buf)` (`ctree.c:511`).
   `copy_extent_buffer_full` (`fs/btrfs/extent_io.c:4197`) copies `src->len` bytes, the full
   nodesize. A new block is not cleared either: `btrfs_init_new_buffer` zeroes only the header
   (`fs/btrfs/extent-tree.c:5303`). So the mechanism Toolan & Humphries give ("not copied") is not
   what the source says.
2. **The write path zeroes the slack of every tree block.** `write_one_eb` calls
   `prepare_eb_write` (`extent_io.c:2215`) before it submits the block. Under the comment "Set
   btree blocks beyond nritems with 0 to avoid stale content" it zeroes, for an internal node,
   from the end of key pointer `nritems` to the end of the block (`extent_io.c:2227`), and for a
   leaf, from the end of item `nritems` to the start of the last item's data
   (`extent_io.c:2239`): exactly the two ranges defined above. The checksum is computed afterwards
   (`btree_csum_one_bio`, `fs/btrfs/disk-io.c:255`), so it covers the zeroed block.
3. **This is old.** The zeroing came with two commits by Liu Bo, "Btrfs: memset to avoid stale
   content in btree node block" (`3eb548ee3a80`) and "... in btree leaf" (`851cd173f060`), both of
   September 2016. Both are ancestors of v4.9 and not of v4.8 (checked with GitHub's compare API).

So their observation should be right, their explanation wrong, and the effect wider than they
report: not only internal nodes and not only the copy, but every tree block the kernel writes,
leaf or node, first write or rewrite, has all-zero slack on disk. A superseded block was written
by the same path as a live one, so it has nothing in its slack either.

**Registered prediction.** For every image of the corpus and for `sandbox.img`:

- **P1 (kernel-written blocks).** Every checksum-valid tree block has zero non-zero bytes in its
  slack: leaves and internal nodes, live, backup-reachable and unreferenced, inside and outside
  the current chunk map.
- **P2 (superseded against live).** For every pair of a superseded block and its successor (same
  tree, same level, same first key, the next surviving generation), both slacks are all-zero.
  There is nothing to compare: the slack of the superseded copy holds no more than that of the
  live one.
- **P3 (blocks `mkfs.btrfs` wrote).** The blocks of generation 1 come from btrfs-progs 6.6.3, not
  from the kernel, and `prepare_eb_write` never saw them. I predict their slack is zero as well,
  because mkfs builds each block in a cleared buffer. This part is from memory of btrfs-progs,
  **not** from reading its source, and is the likeliest to fail.
- **P4 (the prototype's findings on `sandbox.img`).** research.md §10.13 says the prototype
  "recovered such remnants from `sandbox.img`". If P1 holds that cannot be slack content. I
  predict that the prototype saves no leaf slack and counts no internal-slack residuals on
  `sandbox.img`, and that every "orphan item" it reports beyond `nritems` is a false positive: a
  25-byte window that lies inside the zeroed gap cannot parse, so any hit must come from slots
  that run past the gap into live item data (the prototype scans up to 200 slots beyond
  `nritems` without checking where the item data begins).

**What would refute it.** One checksum-valid block with a non-zero slack byte on an image that
only the pinned mkfs and the guest kernel 7.0 have written (P1, P3). The mutated images
(`corpus/mutate.py`) count too: a mutation that lands inside a block breaks its checksum, and only
valid blocks are measured. An image btrfska refuses at the feature gate is recorded as refused.
For P4: a saved leaf-slack file, a
non-zero residual count, or a beyond-`nritems` hit whose 25 bytes lie inside the gap.

**What the outcome means for the paper.** If P1 and P2 hold:
- "Node slack" and "items beyond `nritems`" are **not recovery sources** on any filesystem written
  by Linux 4.9 (December 2016) or later. C1 can keep them only for filesystems last written by an
  older kernel, which this corpus cannot produce, and must say so. What C1 keeps in full are the
  whole superseded blocks (orphan nodes) and the kernel's ORPHAN_ITEM.
- Bhat & Wani 2018's orphan items would then be an artifact of pre-4.9 kernels. Which kernel they
  used is to be checked in their paper before the draft says so.
- Non-zero slack in a checksum-valid block becomes a **tampering signal** (C5): the kernel cannot
  have written it. That covers Toolan & Humphries' internal-node technique and Wani et al.'s W1
  and W2. It also explains why their hidden message is lost on the next write of that node, and
  predicts the same for leaf slack.
- The M4 slack parser is still worth building, as a detector and for old filesystems, but it
  needs a test image with planted slack, since no honest image has any.

If P1 fails, the blocks that carry slack content are described (tree, level, writer, what the
bytes parse as), and C1 stands for those.

## 2. Method

**Images.** Every row of `corpus/manifest.tsv` as built by `corpus/build.py` on this host (15),
plus `sandbox.img`. All are read through `substrate/image.py`, read-only. `m3_wide` is the only
image with internal nodes; its numbers are reported on their own.

**Blocks.** `discover_image(img, fs, full_sweep=True)`: every sector-aligned candidate of the whole
image, so blocks in removed chunks are included. A block counts when it validates (checksum,
fsid, level, `nritems`, layout). Each **physical copy** is measured, because DUP copies are
written separately; the tables count distinct logical blocks (bytenr, generation, level, owner)
and say when two copies of one block differ.

**Slack metric.** For each valid copy: the slack range as defined in §1, its length, and the
number of non-zero bytes in it. For a leaf the start of the item data is the smallest item data
offset (on a valid leaf that is the last item's). A block with non-zero slack is recorded in full:
image, physical offset, bytenr, generation, owner, level, `nritems`, the offsets of the first and
last non-zero byte, and the first 64 non-zero-run bytes in hex.

**Classes.** Each block is reported by level (leaf, internal), by reachability (`live`,
`backup_reachable`, `unreferenced`, from the scan's classification), by placement (inside or
outside the current chunk map) and by writer (generation 1: `mkfs.btrfs`; above 1: the kernel).

**Pairs.** Within one image, valid blocks are grouped by (owner, level, first key). Inside a group,
ordered by generation, each block and the next one form a superseded-successor pair. For each
pair the two non-zero counts are recorded, and a pair is "live-ended" when its successor is live.
First-key matching misses a block whose first item was deleted between two generations; such a
block is still measured under P1, only not paired.

**The prototype (P4).** `legacy/main.py` runs on `sandbox.img` with its output under
`images/scratch/exp/EXP-005/legacy/`. Recorded: `leaf_slacks_found`, `internal_slack_residuals`
and the orphan-item count from its JSON report. Each beyond-`nritems` hit is then located by the
experiment script: slot range against the leaf's zeroed gap.

**Repetitions.** Parsing a fixed image is deterministic: one run per image, with the image's
hash (plan.md §7). The images come from one build on one host. That limits nothing here if P1
holds on every block, because the claim is about a code path and not about counts; §7 will say
what it does limit.

**Success.** P1 to P4 each hold or fail on their own, and are reported either way.
