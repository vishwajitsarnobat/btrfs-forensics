# EXP-009 — How right the timeline is: precision and recall per event type on `m4_deep`

- **Date:** 2026-10-07 (registration, then results)
- **Milestone:** paper readiness (plan.md §8, "E-timeline"; issue #55); claim C3 (`btrfska
  timeline`, plan.md M5d)
- **Script:** [`experiments/exp009.py`](exp009.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-009/results.jsonl` (gitignored), one line per build
- **Registration:** §1 to §3 were committed before the first build of the extended scenario and
  before the script existed. **Not blind:** the timeline of the corpus image `m4_deep` as built
  before this change (no renames, no event log) had been looked at on the same day. It showed 441
  committed `create` events and 8 `log_only` ones, 21 `delete` events (victims 4 to 24, none of
  victims 1 to 3), delete intervals from 1 to 9 generations wide (victim 4: 19 to 28), no
  `order_assumed` on a create or a delete, and one `link` event that the scenario never did
  (`pad/p2`, between generations 20 and 21). The predictions below use that.

## 1. Hypothesis

`btrfska timeline` reports the creates, renames and deletes of a history deeper than the backup
roots without a wrong event, and misses only the events whose evidence is gone: an event is
missed when no surviving state, before or after it, holds the file in the version that would
show it.

Registered for **every** build (N = 5), counting as defined in §2:

- **P1 (create).** Precision 1.0. Recall at least 0.97: what is missed is the creates of files
  whose whole life lies before the oldest state the scan finds (victims and moved files of the
  first rounds).
- **P2 (delete, `never_committed` included).** Precision 1.0. Recall at least 0.80, with a median
  over the builds of at least 0.85.
- **P3 (rename).** Precision 1.0. Recall at least 0.75. A rename is seen only when one state
  holds the old name and a later one the new name, inside a window of three to five commits.
- **P4 (flags).** Of the create, rename and delete events reported, at most 5 % carry
  `order_assumed`. `log_only` is carried by the 16 events of the 8 flash files (8 creates, 8
  `never_committed`) and by nothing else.
- **P5 (delete intervals).** The width of a delete's interval (the generation of the first state
  that no longer holds the file minus that of the last state that does) has a median of at most
  2 and a maximum of at most 12 generations.
- **P6 (events the scenario never does).** At most 5 `link` or `move` events per build, all on
  files whose walk had a gap (not a measured type; reported because they are wrong events).

**What would refute it.** Any precision below 1.0 in P1 to P3: the timeline then reports an event
that did not happen, at a time it did not happen, and C3 cannot be offered without saying when
that occurs. Recall below the registered floors would mean the timeline misses events whose
evidence survives (the script separates the two, §2) or that less survives than the trial
suggests; either is reported as found.

**What it means for the paper.** C3 gets a number: per event type, how many of the timeline's
events are right and how many of the real events it finds, on a history no backup root covers,
with the share of events that rest on an assumed order or on a log tree alone.

## 2. Method

**Scenario.** `corpus/vm/scenarios/deep.guest.sh`, the recipe of `m4_deep` (EXP-006 §2), extended
for this experiment, so that its log is a ground truth for events and not only for content:

- every create, rename and delete in the top-level tree (subvolume 5) is logged as
  `=== EVENT KIND INODE GENERATION PATH [NEW PATH]`, after the `sync` that committed it.
  GENERATION is the superblock's generation then, read in the guest with `btrfs inspect-internal
  dump-super /dev/vda` (it only reads), so it is the transaction the event happened in. INODE is
  `stat -c %i`, which on btrfs is the inode's objectid. A flash file is logged after the sync that
  commits the transaction it lived in;
- every round renames one small inline file: `moves/m_R.txt` is created in round R's padding
  commit, renamed to `moves/m_R.moved` in round R + 1's and deleted in round R + 2's. The
  padding commit is made anyway, so the number of commits does not change;
- the file unlinked while open is logged as `unlink` (its inode stays, under ORPHAN_ITEM) and is
  not one of the measured events.

Per build that is 476 creates (3 directories, 400 padding files, 24 victims, 16 separators, 8
flash files, 24 moved files, the file unlinked while open), 23 renames and 54 deletes (24
victims, 8 flash files, 22 moved files).

**Builds.** Five fresh builds of scenario `deep`, each into its own directory with its own guest
initramfs (the shared `images/vm/initramfs.cpio.gz` is not touched), measured and deleted.

**Measurement per build.** `catalog build --full-sweep`; then the timeline of tree 5 with the
uncommitted sources (`Timeline(conn, tree_id=5, uncommitted=True)`, what `btrfska timeline DB
--tree 5 --uncommitted --json` prints). The image's hash is taken before and after.

**Matching.** The identity of a logged event is (inode, creation generation), the creation
generation being the GENERATION of that inode's `create` line. A reported event of tree 5 matches
a logged event of the same type when:

- `create`: `objectid` and `created` equal the identity (its interval is its exact transaction,
  `created`, so the logged generation must equal it);
- `rename` (and `move`, counted as a rename): identity equal, the new name (`to.name`) equal to
  the logged new name, and the logged generation within `generations`, both ends included;
- `delete` and `never_committed`: identity equal and the logged generation within
  `generations`, both ends included.

Each logged event is matched at most once. **Precision** of a type: matched reported events over
all reported events of that type, except those of inode 256 (the top directory, made by mkfs, not
by the scenario). **Recall**: matched logged events over all logged events of that type. Also
reported: recall over the logged events *within reach*, those of a file that at least one source
of the timeline shows at all, which separates what the tool misses from what the disk lost.

**Also reported.** The share of reported create, rename and delete events with `order_assumed`,
and with `log_only`; the delete interval widths (median, maximum); the count of `link` and `move`
events; whether the `unlink` of the file unlinked while open is reported within its logged
generation.

**Reported.** For every quantity the median and the range over the five builds, and the host.

Prediction by prediction:

- **P1 (create): holds.** Precision 1.0 in every build: all 470 or 471 creates the timeline
  reports carry the creation generation the guest logged. This also checks the log: the
  generation read from the superblock after each `sync` equals the INODE_ITEM's generation for
  every file the timeline holds. Recall 0.987–0.989. The 5 or 6 creates missed are victims 1 to 4
  and `moves/m_1.txt`, `moves/m_2.txt` (`m_1` is seen in builds 4 and 5): files that lived only
  in generations 8 to 20. In a sixth build, made afterwards with the same environment to be
  inspected, the catalog's states are generation 3, generation 10 (whose walk of tree 5 has gaps
  and yields no inode), and 21 to 93: the root trees of generations 11 to 20 did not survive. The
  registered
  explanation ("before the oldest state the scan finds") is therefore loose: the oldest states
  survive, the ones after them do not. Every create of a file that any source shows is found.
- **P2 (delete): refuted for precision, in 2 of 5 builds.** In builds 4 and 5 the timeline
  reports `never_committed` for `moves/m_1.txt` (inode 661, created in generation 10), bounded to
  generations 9 to 10. The file was committed in generation 10, renamed in 14 and deleted in 17.
  The timeline's only view of it is an uncommitted leaf of generation 10 (`orphan_node`); the
  committed state of generation 10 is in the catalog, but its walk has gaps and does not reach
  the file, and no state of 11 to 20 survives. `never_committed` says "no commit held this file",
  and it rests only on the file's absence from the committed states that survive: the same kind
  of conclusion from absence that the timeline refuses to draw for `delete` when a walk has gaps.
  Recall 0.889 in every build (registered floor 0.80, median floor 0.85: holds). The 6 deletes
  missed are those of victims 1 to 4 and of `m_1`, `m_2`: the files P1 misses. Within reach,
  every delete is found except the one P2's wrong event stands for.
- **P3 (rename): holds.** Precision 1.0, recall 0.870 (20 of 23) in every build. The three
  renames missed are those of `m_1`, `m_2`, `m_3` (generations 14, 17, 21). Two of them are
  "within reach" in the sense of §2 but not visible as renames: `m_3` is seen only under its new
  name, in a fragment of generation 21 (the rename's own transaction), and `m_1` (builds 4 and 5)
  only under its old name, in the uncommitted leaf of generation 10. Neither version pair
  survives, so the timeline could not have shown the rename.
- **P4 (flags): holds.** No create, rename or delete event carries `order_assumed`. `log_only`
  is carried by exactly the 16 events of the 8 flash files. The share of measured events with
  either flag is 2.96–2.97 %, all of it `log_only`. (The `unlink` of the file unlinked while
  open, not a measured type, is bounded by two root trees of generation 93 and does carry
  `order_assumed`.)
- **P5 (delete intervals): holds.** Of the 40 `delete` events of each build, 37 are bounded to
  one generation, one to 2, one to 5 and one to 6. In the build inspected afterwards (same
  widths) these are `victim_6` (26 to 28), `moves/m_3.moved` (23 to 28) and `victim_5` (22 to
  28): the walks of 21 to 27 have gaps, so the first state that proves the absence is the whole
  walk of generation 28. `never_committed` events are 1 wide by construction and are not counted
  here.
- **P6 (events the scenario never does): holds.** One `link` per build, on padding file
  `pad/p2`: its versions in states 21 to 23 have no name (those walks have gaps and do not reach
  its INODE_REF), and from state 24 on it has one, so the timeline reports a `link` that never
  happened. No `move`.

## 7. Threats to validity

- **Internal.** The ground truth is the scenario's own log. The generation of an event is read
  after the `sync` that commits it, and would be wrong if a second commit slipped in between;
  create precision 1.0 (the logged generation equals the INODE_ITEM's for every file found) says
  that did not happen for creates, and the scenario's long commit interval makes it unlikely for
  the others. The matching gives the interval both ends, so a delete bounded by a state of the
  delete's own generation (a root tree written in the middle of that transaction) still matches;
  no such event carried `order_assumed`. Five builds on one host gave the same counts except
  where noted, so the spread is small, but this is one scenario and one host class.
- **External.** One scenario, small (512 MiB), no balance, no compression, inline renamed files,
  one rename per file, one subvolume measured; guest kernel 7.0 on virtio. A rename into another
  directory (`move`), hard links, many events between two surviving states, and histories with a
  balance are not measured. The states that survive here (none for generations 11 to 20) are a
  property of this allocation pattern, not of btrfs in general.
- **Construct.** Precision and recall count events with the right identity and an interval that
  contains the truth; they do not reward a narrow interval, which P5 reports separately. "Within
  reach" means that some source shows the file at all, not that the versions an event needs
  survive, so it overstates what the tool could have found (P3). The timeline's other kinds
  (`modify`, `touch`, `attr`, `unlink`) are not measured, except for the one `unlink` and the
  count of `link`/`move` events.

## 8. Status

**Partly refuted.** Creates and renames: no wrong event in five builds, and every event whose
evidence survives is found (renames: every one whose before and after versions survive). Deletes:
recall as predicted, but precision 0.98 in 2 of 5 builds, from one wrong `never_committed`: a
file committed in a generation whose state survives only with gaps is said never to have been
committed. The share of events resting on an assumed order is 0 and on a log tree alone about
3 %, all flash files. The timeline also reports one `link` per build that never happened, from
comparing a version seen through a walk with gaps.

Follow-ups (not done here):

- `never_committed` should need evidence, not absence: for instance, a whole walk of the committed
  state of the generation the file was seen in, which does not hold it; otherwise the ending is
  `not_seen` with a reason. The same care applies to name changes between versions seen through
  walks with gaps (`link`, `unlink`, `rename`). A fix is a change of the timeline's documented
  semantics (README, plan.md M5d) and is left to a separate pull request, after which this
  experiment is re-run.
- Scenarios with moves, hard links and several events between surviving states, so that `move`,
  `link` and net effects get numbers too.
