# EXP-009 — How right the timeline is: precision and recall per event type on `m4_deep`

- **Date:** 2026-10-07 (registration)
- **Milestone:** paper readiness (plan.md §8, "E-timeline"; issue #55); claim C3 (`btrfska
  timeline`, plan.md M5d)
- **Script:** [`experiments/exp009.py`](exp009.py); environment: [`experiments/env.sh`](env.sh)
- **Raw outputs:** `images/scratch/exp/EXP-009/results.jsonl` (gitignored), one line per build
- **Registration:** §1 to §3 were committed before the first build of the extended scenario and
  before the script existed. **Not blind:** the timeline of the corpus image `m4_deep` as built
  before this change (no renames, no event log) had been looked at on the same day. It showed 441
  committed `create` events and 8 `log_only` ones, 21 `delete` events (victims 4 to 24, none of
  victims 1 to 3), delete intervals from 1 to 9 generations wide (victim 4: 19 to 28), no
  `order_assumed` on a create or a delete, and one `link` event that the scenario never did
  (`pad/p2`, between generations 20 and 21). The predictions below use that.

## 1. Hypothesis

`btrfska timeline` reports the creates, renames and deletes of a history deeper than the backup
roots without a wrong event, and misses only the events whose evidence is gone: an event is
missed when no surviving state, before or after it, holds the file in the version that would
show it.

Registered for **every** build (N = 5), counting as defined in §2:

- **P1 (create).** Precision 1.0. Recall at least 0.97: what is missed is the creates of files
  whose whole life lies before the oldest state the scan finds (victims and moved files of the
  first rounds).
- **P2 (delete, `never_committed` included).** Precision 1.0. Recall at least 0.80, with a median
  over the builds of at least 0.85.
- **P3 (rename).** Precision 1.0. Recall at least 0.75. A rename is seen only when one state
  holds the old name and a later one the new name, inside a window of three to five commits.
- **P4 (flags).** Of the create, rename and delete events reported, at most 5 % carry
  `order_assumed`. `log_only` is carried by the 16 events of the 8 flash files (8 creates, 8
  `never_committed`) and by nothing else.
- **P5 (delete intervals).** The width of a delete's interval (the generation of the first state
  that no longer holds the file minus that of the last state that does) has a median of at most
  2 and a maximum of at most 12 generations.
- **P6 (events the scenario never does).** At most 5 `link` or `move` events per build, all on
  files whose walk had a gap (not a measured type; reported because they are wrong events).

**What would refute it.** Any precision below 1.0 in P1 to P3: the timeline then reports an event
that did not happen, at a time it did not happen, and C3 cannot be offered without saying when
that occurs. Recall below the registered floors would mean the timeline misses events whose
evidence survives (the script separates the two, §2) or that less survives than the trial
suggests; either is reported as found.

**What it means for the paper.** C3 gets a number: per event type, how many of the timeline's
events are right and how many of the real events it finds, on a history no backup root covers,
with the share of events that rest on an assumed order or on a log tree alone.

## 2. Method

**Scenario.** `corpus/vm/scenarios/deep.guest.sh`, the recipe of `m4_deep` (EXP-006 §2), extended
for this experiment, so that its log is a ground truth for events and not only for content:

- every create, rename and delete in the top-level tree (subvolume 5) is logged as
  `=== EVENT KIND INODE GENERATION PATH [NEW PATH]`, after the `sync` that committed it.
  GENERATION is the superblock's generation then, read in the guest with `btrfs inspect-internal
  dump-super /dev/vda` (it only reads), so it is the transaction the event happened in. INODE is
  `stat -c %i`, which on btrfs is the inode's objectid. A flash file is logged after the sync that
  commits the transaction it lived in;
- every round renames one small inline file: `moves/m_R.txt` is created in round R's padding
  commit, renamed to `moves/m_R.moved` in round R + 1's and deleted in round R + 2's. The
  padding commit is made anyway, so the number of commits does not change;
- the file unlinked while open is logged as `unlink` (its inode stays, under ORPHAN_ITEM) and is
  not one of the measured events.

Per build that is 476 creates (3 directories, 400 padding files, 24 victims, 16 separators, 8
flash files, 24 moved files, the file unlinked while open), 23 renames and 54 deletes (24
victims, 8 flash files, 22 moved files).

**Builds.** Five fresh builds of scenario `deep`, each into its own directory with its own guest
initramfs (the shared `images/vm/initramfs.cpio.gz` is not touched), measured and deleted.

**Measurement per build.** `catalog build --full-sweep`; then the timeline of tree 5 with the
uncommitted sources (`Timeline(conn, tree_id=5, uncommitted=True)`, what `btrfska timeline DB
--tree 5 --uncommitted --json` prints). The image's hash is taken before and after.

**Matching.** The identity of a logged event is (inode, creation generation), the creation
generation being the GENERATION of that inode's `create` line. A reported event of tree 5 matches
a logged event of the same type when:

- `create`: `objectid` and `created` equal the identity (its interval is its exact transaction,
  `created`, so the logged generation must equal it);
- `rename` (and `move`, counted as a rename): identity equal, the new name (`to.name`) equal to
  the logged new name, and the logged generation within `generations`, both ends included;
- `delete` and `never_committed`: identity equal and the logged generation within
  `generations`, both ends included.

Each logged event is matched at most once. **Precision** of a type: matched reported events over
all reported events of that type, except those of inode 256 (the top directory, made by mkfs, not
by the scenario). **Recall**: matched logged events over all logged events of that type. Also
reported: recall over the logged events *within reach*, those of a file that at least one source
of the timeline shows at all, which separates what the tool misses from what the disk lost.

**Also reported.** The share of reported create, rename and delete events with `order_assumed`,
and with `log_only`; the delete interval widths (median, maximum); the count of `link` and `move`
events; whether the `unlink` of the file unlinked while open is reported within its logged
generation.

**Reported.** For every quantity the median and the range over the five builds, and the host.
